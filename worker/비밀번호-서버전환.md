# 로그인 비밀번호 서버 저장 — 한 번만 하면 되는 설정 (v9.97)

**왜:** 지금까지 비밀번호는 각 폰·PC에만 저장돼서, 앱을 지웠다 다시 깔거나 폰을 바꾸면 초기 비밀번호로 돌아갔습니다. 초기 비밀번호도 앱 코드와 매뉴얼에 그대로 적혀 있었습니다.
**이제:** 비밀번호를 Supabase 서버에 **bcrypt 해시**로만 저장합니다. 공개 키로는 비밀번호 표를 읽거나 쓸 수 없고, 확인·변경용 함수 3개만 부를 수 있습니다.

> 앱(v9.97)은 이미 배포돼 있고, **아래 SQL을 실행하기 전까지는 예전과 똑같이** 동작합니다. 실행하는 순간부터 서버 방식으로 바뀝니다.

## 실행 (대표, 2분)

1. 깃허브 `worker/supabase_passwords.sql` 을 열어 전체 복사합니다.
2. [supabase.com](https://supabase.com) 로그인 → 내셔널짐 프로젝트 → 왼쪽 **SQL Editor** → **New query** → 붙여넣기.
3. 붙여넣은 내용 위쪽의 이 줄에서 `<<여기에 관리자 비밀번호>>` 를 **대표가 쓸 관리자 비밀번호(8자 이상)** 로 바꿉니다. 따옴표는 그대로 두세요.
   ```
   declare admin_pw text := '<<여기에 관리자 비밀번호>>';
   ```
   (안 바꾸면 "관리자 비밀번호를 적은 뒤 실행하세요" 오류가 나고 **아무것도 바뀌지 않습니다.**)
4. **RUN**. `Success` 가 나오면 끝입니다.
5. 실행 뒤 SQL Editor 왼쪽 목록에서 **방금 쿼리를 삭제**하세요(관리자 비밀번호가 평문으로 남지 않게). 다시 실행할 일이 생기면 그때 다시 붙여넣으면 됩니다(이미 있는 비밀번호는 건드리지 않음).

관리자 비밀번호는 공개된 초기값(`admin0000`)을 **쓰지 않고** 대표가 적은 값으로 만들어집니다. 그래야 SQL을 실행한 직후 다른 사람이 초기값으로 관리자 비밀번호를 먼저 바꿔 버리는 일이 없습니다. 직원 계정은 지금의 초기 비밀번호로 시작하되 아래처럼 첫 로그인 때 바로 바뀝니다.

## 실행 후 직원들이 겪는 일

| 상황 | 어떻게 되나 |
|---|---|
| 아직 초기 비밀번호를 쓰던 직원 | 초기 비밀번호로 들어가면 **"새 비밀번호 정하기"** 창이 뜹니다(6자 이상). 정한 비밀번호가 서버에 저장됩니다. ("나중에"를 누르면 다음 로그인 때 다시 물어봅니다) |
| 자기 폰에서 비밀번호를 바꿔 쓰던 직원 | 그 폰에서 **쓰던 비밀번호 그대로** 들어가면 앱이 자동으로 서버에 옮깁니다. Face ID·자동 로그인으로 들어와도 앱이 뒤에서 한 번 옮깁니다. 따로 할 일이 없습니다. |
| 앱을 지웠다 다시 깔았거나 새 폰 | 서버에 저장한 비밀번호로 그대로 들어갑니다. |
| 비밀번호를 잊은 직원 | 대표가 관리자로 로그인 → 마이페이지 **🔑 직원 비밀번호 초기화** → 직원을 고르고 임시 비밀번호(6자 이상)를 정해 줍니다. 직원은 임시 비밀번호로 들어가자마자 새 비밀번호를 정합니다. |
| 초기·임시 비밀번호를 14일 안에 안 바꿈 | 그 비밀번호는 만료됩니다(누가 초기값으로 가로채는 틈을 줄이기 위해). 대표가 **직원 비밀번호 초기화**로 다시 임시 비밀번호를 정해 주면 됩니다. |
| 같은 계정으로 10번 틀림 | 10분 동안 잠깁니다. 단, **그 기기에서 이미 맞게 들어간 적이 있으면** 잠겨 있어도 맞는 비밀번호로 들어갑니다(누가 일부러 틀려서 잠가 두는 장난 방지). |
| 인터넷이 끊긴 상태 | 그 기기에서 서버로 한 번이라도 맞게 들어간 계정은 오프라인에서도 들어갑니다(비밀번호를 해시로만 기억). 처음 쓰는 계정은 인터넷이 필요합니다. 서버 응답이 8초 넘게 없으면 오프라인으로 봅니다. |

- 초기 비밀번호는 서버에 처음 한 번 들어가는 용도로만 씁니다. 매뉴얼에서는 지웠으니, 직원에게는 대표가 직접 알려 주세요.
- 비밀번호는 **직원 6자 이상, 관리자 8자 이상**(64자 이하).
- 한 사람이 여러 기기에서 **서로 다른** 비밀번호를 쓰고 있었다면, 먼저 로그인한 기기의 비밀번호가 서버에 올라갑니다. 다른 기기에서는 "이 기기에서 쓰던 비밀번호는 더 이상 안 돼요" 안내가 뜨고, 서버에 올라간 비밀번호로 들어가면 됩니다.
- 기기에서 쓰던 비밀번호가 5자 이하라서 서버로 못 옮기는 경우에도 안내가 뜹니다. 대표가 초기화해 주세요.
- 생체 로그인(Face ID·지문)과 "이 기기 자동 로그인"은 예전과 같습니다. 각 기기에만 저장되므로 앱을 다시 깔면 다시 등록해야 합니다.

## 확인

실행 후 **관리자**로 비밀번호 로그인을 한 번 해 보세요(SQL에 적은 비밀번호). 들어가지면 서버 방식이 동작하는 것입니다. 직원은 초기 비밀번호로 들어가면 "새 비밀번호 정하기" 창이 떠야 합니다.

## 운영 중 필요할 때 (Supabase SQL Editor 에서 한 줄 실행)

- 누가 일부러 틀려서 잠가 둔 계정 풀기(예: 관리자):
  `update private.app_passwords set failed = 0, locked_until = null where key = '관리자';`
- 관리자 비밀번호를 잊었을 때 새로 정하기(앱의 "직원 비밀번호 초기화"는 관리자 자신에게는 쓸 수 없음):
  `update private.app_passwords set hash = extensions.crypt('새비밀번호8자이상', extensions.gen_salt('bf', 10)), must_change = false, failed = 0, locked_until = null, updated_at = now() where key = '관리자';`
  (실행 뒤 쿼리 삭제)

## 다음 단계 (모두 한 번씩 서버로 로그인한 뒤)

앱 코드에 남아 있는 초기 비밀번호(이전용)를 다음 버전에서 지웁니다. 직원 전원이 한 번씩 로그인했으면 Claude에게 "비밀번호 초기값 코드에서 지워 줘"라고 요청하세요.

## 되돌리기 (비상시에만)

SQL Editor에서 `worker/supabase_passwords.sql` 맨 아래 주석의 `drop ...` 다섯 줄을 실행하면, 앱은 예전 방식(기기 저장)으로 돌아갑니다. 이 경우 서버로 옮긴 비밀번호는 사라지고 초기 비밀번호로 돌아가니, 정말 필요할 때만 쓰세요.

## 기술 메모

- 표: `private.app_passwords(key, hash, must_change, failed, locked_until, updated_at)` — `private` 스키마는 API로 노출되지 않습니다. RLS를 켰고 정책은 없습니다.
- 함수(`security definer`, `search_path=''`, `for update nowait`): `public.pw_login(p_key, p_pw)`, `public.pw_change(p_key, p_old, p_new)`, `public.pw_admin_reset(p_admin_pw, p_target, p_new)`. anon·authenticated에는 이 3개의 EXECUTE만 줍니다. `pw_admin_reset`은 대상이 `'관리자'`면 거절합니다. `must_change` 행은 `updated_at` 기준 14일 뒤 만료.
- 앱: `verifyPassword()`·`pwServer`(8초 제한)·`pwCache`(PBKDF2)·`pwClaimAfterLogin()`(js/app_core.js), `submitPasswordChange()`·`submitPwReset()`(js/app_handlers.js). 함수가 없으면(PGRST202) 예전 로직으로 동작합니다.
- 검증: 로컬 Postgres 16(anon/authenticated 역할, extensions 스키마)에서 SQL 전 경로 + Playwright(실제 index.html + Supabase 스텁) 56개 시나리오. 적대적 리뷰(SQL 보안/앱 흐름/Supabase 호환)에서 나온 11건 반영.
- 로그인 비밀번호는 화면에 들어가는 문을 지키는 용도입니다. 회원 데이터 자체의 보호는 `보안_읽기전용_전환가이드.md`(RLS 읽기 전용 + 워커 쓰기)가 담당합니다.
